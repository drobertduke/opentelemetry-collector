# Integrating a Ring-Buffer Telemetry Query Service into OpenTelemetry Collector

## Introduction and Goals  
OpenTelemetry Collector (OTEL Collector) is a flexible service for receiving, processing, and exporting telemetry data (traces, metrics, logs) ([Configuration | OpenTelemetry](https://opentelemetry.io/docs/collector/configuration/#:~:text=Configuration%20structure)). In its default form, the Collector is a one-way pipeline: data comes in through **receivers**, passes through **processors**, and goes out via **exporters** ([Configuration | OpenTelemetry](https://opentelemetry.io/docs/collector/configuration/#:~:text=Configuration%20structure)). Our goal is to enhance the Collector with a **ring-buffer-based telemetry query service** that buffers incoming telemetry and allows querying it on demand. This service will: 

- Ingest OTLP-formatted telemetry (traces, metrics, logs) via the standard OTLP gRPC receiver.  
- Store each type of telemetry data in an in-memory **ring buffer** (a fixed-size circular buffer) with configurable size per data type.  
- Expose a new **gRPC API** for clients to query the buffered data with various filters (e.g. by timestamp range, span ID, resource attributes).  
- Support an optional “**immediate**” or streaming mode where new telemetry is pushed to the client in real-time as it arrives.  

The following sections outline an integration plan, covering how to fit this into the OTEL Collector architecture, how to implement the ring buffers, design of the query API, performance considerations, and references to similar efforts for inspiration. 

## Integration with OTEL Collector Architecture  
**Collector Components:** The OTEL Collector supports custom components in its architecture: receivers, processors, exporters (which are part of pipelines and handle telemetry data directly), and **extensions** (which add auxiliary capabilities and typically do not handle pipeline data) ([Configuration | OpenTelemetry](https://opentelemetry.io/docs/collector/configuration/#:~:text=After%20each%20pipeline%20component%20is,section%20of%20the%20configuration%20file)) ([Configuration | OpenTelemetry](https://opentelemetry.io/docs/collector/configuration/#:~:text=Besides%20pipeline%20components%20you%20can,through%20the%20%20600%20section)). For this feature, we need both to handle incoming telemetry (to buffer it) and to serve a new API. This suggests using a combination of a **processor** (or possibly an exporter) and an **extension**: 

- **Processor for Buffering:** A custom processor in the pipelines can intercept incoming telemetry and copy it into the in-memory ring buffer. Processors have direct access to trace, metric, or log data as it passes through, making them suitable for buffering. Using a processor means the data can still continue through the pipeline to other exporters (so normal processing/export isn’t disrupted, unless we choose to only buffer). We can implement one processor for each data type or a single processor that implements all three (traces, metrics, logs) if we register it accordingly.  

- **Extension for Query Service:** The query service will run as a separate server (exposing new gRPC endpoints). This is best implemented as an OTEL Collector **extension**, since extensions are intended for auxilliary servers or background tasks that are not part of the data pipelines ([Configuration | OpenTelemetry](https://opentelemetry.io/docs/collector/configuration/#:~:text=Besides%20pipeline%20components%20you%20can,through%20the%20%20600%20section)). For example, the Collector’s health_check, pprof, and zPages are extensions that run HTTP servers for diagnostics ([opentelemetry-collector/extension/README.md at main · open-telemetry/opentelemetry-collector · GitHub](https://github.com/open-telemetry/opentelemetry-collector/blob/main/extension/README.md#:~:text=Extensions%20provide%20capabilities%20on%20top,allows%20fetching%20Collector%27s%20performance%20profile)) ([opentelemetry-collector/extension/zpagesextension/README.md at main · open-telemetry/opentelemetry-collector · GitHub](https://github.com/open-telemetry/opentelemetry-collector/blob/main/extension/zpagesextension/README.md#:~:text=Enables%20an%20extension%20that%20serves,receivers%20provide%20some%20zPage%20instrumentation)). Our query service extension will similarly run a gRPC server to handle client query requests. The extension can be started alongside the pipelines (configured under the `service.extensions` in the Collector config) ([opentelemetry-collector/extension/README.md at main · open-telemetry/opentelemetry-collector · GitHub](https://github.com/open-telemetry/opentelemetry-collector/blob/main/extension/README.md#:~:text=The%20order%20extensions%20are%20specified,in%20the%20configuration%20file%2C%20example)). We will ensure the extension has access to the ring buffer data populated by the processor (e.g. via shared data structures or a global singleton).

**Recommended Approach:** Implement a **custom processor + extension pair**. The processor’s job is to feed data into the ring buffers, and the extension’s job is to expose the query interface. This separation follows OTEL’s design (processing vs. service extension) and allows independent configuration of each. In practice, this means writing a new processor component (implementing the `component.TracesProcessor`, `MetricsProcessor`, `LogsProcessor` interfaces from the Collector SDK) and a new extension (implementing `component.Extension`). We will then create a custom Collector build that includes these components. The OpenTelemetry Collector Builder tool (`ocb`) can be used to create a custom distribution that bundles our new processor and extension along with standard components ([Extending the OpenTelemetry Collector with your own components | by Juraci Paixão Kröhling | OpenTelemetry | Medium](https://medium.com/opentelemetry/extending-the-opentelemetry-collector-with-your-own-components-64c10cf675db#:~:text=We%20have%20now%20our%20processor,have%20two%20options%20to%20explore)) ([Building a custom collector | OpenTelemetry](https://opentelemetry.io/docs/collector/custom-collector/#:~:text=The%20OpenTelemetry%20Community%20developed%20a,components%20that%20are%20publicly%20available)). (This is the same approach used by other custom Collector distributions like **Jaeger v2**). Notably, *Jaeger v2* is itself built on the OTEL Collector and includes a **“Jaeger Query” extension** to serve trace query API and UI within the collector process ([Architecture — Jaeger documentation
](https://www.jaegertracing.io/docs/next-release-v2/architecture/#:~:text=The%20Jaeger%20binary%20is%20build,OpenTelemetry%20Collector%20framework%20and%20includes)) ([Architecture — Jaeger documentation
](https://www.jaegertracing.io/docs/next-release-v2/architecture/#:~:text=storage%20backend%20configured%20in%20the,Jaeger%20Storage%20Extension)). This is a strong proof of concept that adding a query service as an extension is feasible and aligns with best practices. Jaeger’s custom components (e.g. a storage exporter and query extension) are registered in a custom build ([Architecture — Jaeger documentation
](https://www.jaegertracing.io/docs/next-release-v2/architecture/#:~:text=The%20Jaeger%20binary%20is%20build,OpenTelemetry%20Collector%20framework%20and%20includes)), and our approach will be analogous (but for a generic telemetry buffer query service, not tied to Jaeger’s storage). 

**Alternative Considerations:** Another possible approach would be implementing the buffer as an **exporter** (since exporters also see the data) that doesn’t actually send out but stores data. However, making an exporter simultaneously serve queries is unconventional. Using a processor + extension cleanly separates concerns. Forking the Collector’s core is not ideal since the Collector provides extension points; a fork would make maintenance harder unless absolutely necessary. By using the official extension/processor model, we benefit from Collector’s lifecycle management (starting, shutting down components in order ([opentelemetry-collector/extension/README.md at main · open-telemetry/opentelemetry-collector · GitHub](https://github.com/open-telemetry/opentelemetry-collector/blob/main/extension/README.md#:~:text=The%20order%20extensions%20are%20specified,in%20the%20configuration%20file%2C%20example))) and avoid diverging from upstream. 

## In-Memory Ring Buffer Implementation  
Each telemetry data type (traces, metrics, logs) will be stored in its own ring buffer with independent capacity settings. A **ring buffer** is a fixed-size circular queue that overwrites the oldest entries when it reaches capacity. This ensures bounded memory usage: old telemetry will be dropped when the buffer is full, making space for new data. The size limit for each buffer should be **configurable** (e.g. in number of spans, number of log records, number of metric points or data batches, or in total bytes). Configuration might look like: 
```yaml
processors:
  telemetry_buffer:
    traces_buffer_size: 10000     # number of spans to keep
    metrics_buffer_size: 1000     # number of metric data batches to keep
    logs_buffer_size: 5000        # number of log records to keep
```
*(Exact units to be decided; could be count of OTLP messages or timeframe retention.)*

**Data Structures:** In Go, we can implement the ring buffers as slices or arrays with an index that wraps around. For example, for a traces buffer, we maintain an array of span data and an index pointer for the next write position. When new data comes in, it is placed at the current index and the index is incremented modulo the capacity. A simple approach uses a mutex to guard writes and reads. If multiple telemetry items arrive concurrently (the Collector’s pipelines are multi-goroutine), the buffer writes need synchronization. The overhead should be minimal if using an efficient lock or atomic operations for a circular index. The OpenTelemetry Collector’s own exporter queue uses a similar concept of a bounded memory queue (described as a “memory-based ring buffer queue”) for buffering telemetry before export ([exporterqueue package - go.opentelemetry.io/collector/exporter/exporterqueue - Go Packages](https://pkg.go.dev/go.opentelemetry.io/collector/exporter/exporterqueue#:~:text=Queue%20defines%20a%20producer,collector%2Fissues%2F8122%20is%20resolved)). That internal queue implementation can inspire our design. For instance, it likely uses a lock or atomic counter to handle concurrent producers and consumers. 

We might leverage an existing library or pattern for efficiency. One high-performance option is the **LMAX Disruptor** pattern, which is essentially a lock-free ring buffer with sequence counters to manage concurrent producers and consumers ([Optimizing OpenTelemetry's Span Processor for High Throughput and Low CPU Costs](https://careersatdoordash.com/blog/optimizing-opentelemetrys-span-processor/#:~:text=,available%20for%20consumers%20to%20read)). In a disruptor, producers claim the next slot using an atomic increment and write to it, and consumers track a read sequence ([Optimizing OpenTelemetry's Span Processor for High Throughput and Low CPU Costs](https://careersatdoordash.com/blog/optimizing-opentelemetrys-span-processor/#:~:text=,available%20for%20consumers%20to%20read)). This minimizes locking and can achieve very high throughput. DoorDash’s engineering team demonstrated using a Disruptor-based ring buffer in a span processor to significantly increase throughput and reduce GC overhead in OpenTelemetry pipelines ([Optimizing OpenTelemetry's Span Processor for High Throughput and Low CPU Costs](https://careersatdoordash.com/blog/optimizing-opentelemetrys-span-processor/#:~:text=,and%20have%20different%20waiting%20strategies)). They noted benefits like using a preallocated ring buffer to avoid allocations and using atomic cursors to reduce lock contention ([Optimizing OpenTelemetry's Span Processor for High Throughput and Low CPU Costs](https://careersatdoordash.com/blog/optimizing-opentelemetrys-span-processor/#:~:text=,available%20for%20consumers%20to%20read)). If our use-case expects extremely high incoming telemetry volume or many concurrent writers, a disruptor-style implementation (via a Go port such as **`github.com/five-vee/go-disruptor`** which is GC-free when running ([disruptor package - github.com/five-vee/go-disruptor - Go Packages](https://pkg.go.dev/github.com/five-vee/go-disruptor#:~:text=LMAX%20Disruptor%20written%20in%20Go))) could be considered. However, this adds complexity and is typically only justified if performance benchmarks show the simpler mutex approach is insufficient ([disruptor package - github.com/five-vee/go-disruptor - Go Packages](https://pkg.go.dev/github.com/five-vee/go-disruptor#:~:text=,a%20Disruptor%20Over%20Channels)). In many scenarios, a simpler ring buffer (with a mutex or RWLock per buffer) is likely adequate and easier to maintain ([disruptor package - github.com/five-vee/go-disruptor - Go Packages](https://pkg.go.dev/github.com/five-vee/go-disruptor#:~:text=,implications%20and%20ensure%20you%20manage)). We will make a design choice based on desired throughput: start with a clear, correct solution (e.g. a mutex-protected circular buffer) and optimize with lock-free patterns if needed.

**Storing Telemetry Entries:** We must decide what each buffer element contains. For traces, the natural unit might be an individual **span** or an entire **trace** (collection of spans). For metrics, it could be a data point, a metric time series, or an incoming batch. For logs, each log record is a unit. A straightforward approach is to store data in the same format that the Collector uses internally – the OTEL Collector SDK has in-memory representations (pdata structures) for spans, metrics, and logs (e.g. `pdata.Traces` which contains a list of ResourceSpans, etc.). Our processor will receive batches of data (e.g. a `pdata.Traces` object containing potentially many spans). We can iterate through these and store each span separately in the ring, or store the whole batch as one entry. Storing each span/log individually allows fine-grained query filtering (by span ID, attributes, etc.), at the cost of potentially more overhead to split batches. Alternatively, storing the batch intact is simpler and faster, but then queries might need to scan within each batch. For metrics, a batch might contain many data points across different metric instruments; queries by timestamp might be easier if we break those down. As an initial design, we can push individual telemetry records into the ring (one span or one log entry at a time, and perhaps one metric data point or one metric time series at a time). This provides a uniform approach for querying. 

The ring buffer will likely hold pointers or copies of these records. We should be careful about memory usage: copying data could be expensive if metrics batches are large. We might choose to store pointers to the pdata objects or protos, but ensure that the lifespan is managed (since the pipeline might reuse buffers). It could be safer to deep-copy the items into our own structures. Since the buffer is finite, worst-case memory usage is bounded by the buffer capacity times the size of each entry. This should be taken into account for configuration (e.g. 10k spans could consume roughly X MB). We could also allow configuring a maximum **time** to retain data (e.g. drop anything older than N minutes) in addition to fixed size, but a pure ring buffer by count is simpler and usually sufficient.

**Concurrency and Thread-Safety:** The processor will be the **producer** writing to these buffers. The query service will act as a **consumer** (reading from buffers when servicing a query). There may be multiple readers (multiple client requests) and one or multiple producers (the Collector can have multiple pipeline routines pushing data). Thus, the buffers need to handle multi-producer, multi-consumer concurrency. Using Go’s channels is one way, but channels don’t support random access queries or filtering – we need a data structure we can scan. So a manual synchronization is needed. We can protect the buffer with a mutex for both read and write (which is simple but means queries might briefly block new writes) or use RWLock (allowing multiple readers concurrently, blocking only during write operations). The performance impact should be low if queries are relatively infrequent or if the buffer size is not extremely large. If queries become frequent and heavy, more sophisticated lock-free reads (like versioning or copy-on-write snapshots) could be considered. In the initial design, a reasonable approach is a single mutex-protected circular buffer per data type, supporting atomic append and iterative read. Each query can safely traverse the buffer snapshot under lock or by copying out the current content.

We should also consider that the act of buffering should not significantly slow down the normal pipeline. The processor can run asynchronously if needed (e.g. spawn a goroutine to copy data into the buffer so the pipeline thread isn’t delayed). However, since processors are typically called synchronously in the Collector pipeline, doing an asynchronous handoff might complicate ensuring data is buffered before query. A middle-ground is to perform minimal work in the processor (just push into the ring buffer quickly). A properly designed ring buffer (O(1) insert) will make the overhead negligible. For example, the OTel Collector’s built-in batch processor and queue exporters manage thousands of spans per second with minimal overhead by using efficient synchronization primitives ([Optimizing OpenTelemetry's Span Processor for High Throughput and Low CPU Costs](https://careersatdoordash.com/blog/optimizing-opentelemetrys-span-processor/#:~:text=,available%20for%20consumers%20to%20read)).

## gRPC Query API Design  
We will design a new **gRPC service** (or services) that clients can use to query and subscribe to telemetry data from the buffers. This will involve defining Protocol Buffer messages and service RPC methods for traces, metrics, and logs queries. Key considerations for the API design include: the query **filter parameters**, the **response format**, and how to handle **streaming** updates.

**Service Definition:** One approach is to define a unified service like `TelemetryQueryService` with multiple RPC methods, for example: 

- `rpc QueryTraces(TraceQueryRequest) returns (TraceQueryResponse);`  
- `rpc QueryMetrics(MetricsQueryRequest) returns (MetricsQueryResponse);`  
- `rpc QueryLogs(LogsQueryRequest) returns (LogsQueryResponse);`  

Alternatively, we could split into separate services by data type (e.g. `TraceQueryService`) especially if we anticipate separate clients for each. But a unified service is simpler for clients to implement and can share authentication, etc.

**Query Filters:** The request message will contain fields to filter the results. For example, a `TraceQueryRequest` might include: 
- **Time range**: start and end timestamps to select spans within a timeframe. This is useful to query recent data (e.g. last 5 minutes of traces).  
- **Trace ID or Span ID**: to retrieve a specific trace or span. If a trace ID is provided, the response could return all spans in that trace (if they are in the buffer). If a span ID is provided, possibly return that span and its context.  
- **Resource attributes**: match telemetry from a specific service, host, or any attribute that was in the Resource (for example, only spans where `service.name = "checkout-service"`).  
- **Span attributes or Log content**: we might allow a filter expression on attributes (like find all log records where `level=ERROR` or all spans where an attribute `http.status_code >= 500`). This can be quite powerful but adds complexity – a simpler initial implementation might limit to basic equality matching on a few key fields.  
- **Limit**: maximum number of results to return, in case the buffer has a lot of data matching the filter.  

The `MetricsQueryRequest` would have analogous filters: time range, maybe a metric name or instrument type filter, resource attributes, etc. Logs similarly: time range, severity level, logger name, message substring, etc. We should decide on the filtering capabilities based on use cases (e.g. debugging specific traces vs. broad monitoring). To start, focusing on time range and identifiers (IDs or resource attributes) is reasonable.

**Response Format:** We want the response to carry the actual telemetry data that matches the query. We can reuse the existing OTLP data model to avoid reinventing data structures. For example, `TraceQueryResponse` could embed an array of OTLP **ResourceSpans** (the same message used in OTLP trace export) ([Architecture — Jaeger documentation
](https://www.jaegertracing.io/docs/next-release-v2/architecture/#:~:text=storage%20backend%20configured%20in%20the,Jaeger%20Storage%20Extension)), or perhaps an array of **Span** messages. Using the OTLP `ResourceSpans` / `InstrumentationLibrarySpans` wrappers might be slightly heavy, but it ensures compatibility with existing proto definitions. Since the collector’s internal data (`pdata.Traces`) can be easily marshaled to the OTLP protobuf messages, we can leverage that. Similarly, `MetricsQueryResponse` can contain OTLP `ResourceMetrics` (with Metric data points inside), and `LogsQueryResponse` contains `ResourceLogs`. By using standard OTLP message types in the response, clients can use the same generated code they use for OTLP ingestion to parse the results. (We will document that the query service returns data in the same format as if it was an OTLP export, just filtered.)

If needed, we can define our own slim response types (especially if we implement complex filtering or partial data). But initially, reusing OTLP ensures completeness of information (all span fields, metric fields are there). We just need to decide if the query returns entire collected batches or individual records. For traces, likely we gather matching spans and group them by trace ID in ResourceSpans for convenience.

**Single Request vs Streaming:** The **“immediate mode”** requirement suggests that clients might open a subscription to get data continuously. There are two ways to accommodate this in gRPC:

1. **Server-Side Streaming RPC:** The client sends one request (with filter parameters indicating what they want to subscribe to, or perhaps a special flag for streaming), and the server keeps the call open and streams back results as they become available. For example: 
   ```proto
   rpc SubscribeTraces(TraceQueryRequest) returns (stream TraceQueryResponse);
   ``` 
   The server could initially send any currently buffered data that matches the filter (e.g. all spans from last 5 min for service X), and then continue to push new spans as they arrive (that meet the filter). This is analogous to a “tail -f” on logs or a live feed. 

2. **Bidirectional or long-lived channel:** Alternatively, a bidirectional stream could be used, but probably unnecessary here – the requests don’t need to keep sending data from client after initial filter criteria. So server-streaming is sufficient.

We will likely implement a separate streaming method (like `SubscribeTraces`) distinct from a one-time `QueryTraces` method. This makes the API usage clear (one is polling on demand, the other is subscribing). The immediate mode can be optional – if a user just calls `QueryTraces` without streaming, they get a snapshot of current buffer data matching the query. If they call `SubscribeTraces`, they get a stream that will emit new data until they cancel.

**Implementing Query Logic:** When a query request comes in, the extension’s gRPC server will call our handler which needs to read from the ring buffer. A naive implementation will simply iterate over the ring buffer entries and filter each one against the query criteria. Given the buffer is in memory and likely bounded to thousands of entries, this linear scan is extremely fast (a few thousand or even hundred thousand in-memory checks is fine). If needed, we can optimize with indices (for example, keep a map from trace ID to indices for quick trace lookup, or partition logs by severity for quick filtering). Such indices add complexity and memory overhead, and might be premature optimization. Initially, a linear scan with efficient comparison (since everything is in Go memory) should suffice.

For time-range filtering, if the buffer is kept roughly sorted by arrival time (which it naturally is, since it’s append in order), we could optimize by stopping the scan once we go past the end time (since older entries will be at one end of the buffer). But since it’s circular, careful handling is needed (the newest item might wrap to beginning of array). We can simplify by not strictly sorting by timestamp if not needed, but typically the insertion order will correlate with event timestamps.

For an ID lookup (trace ID), scanning may be fine, but for a very specific query like a single trace ID, perhaps having a small map of traceID->list of spans in buffer could return results instantly. We could implement this as an enhancement (maintain a secondary index map in the processor whenever it adds a span, map trace ID to span references). This would speed up trace queries significantly. It’s a design trade-off: if one key use-case is “get me this trace by ID if it’s still in recent memory,” then an index map is helpful. Since traceIDs are typically high-cardinality, the map would at most hold as many entries as the buffer (each span in buffer is in the map). That could double memory usage but still likely fine. For simplicity, we might start without it, and rely on scanning until performance dictates adding it.

**Streaming New Data to Clients:** For the immediate mode (subscribe RPC), the server-side implementation can be tricky. We will need a mechanism to **notify** the query service when new data arrives that might match a subscription. A straightforward approach: when a client subscribes with certain filters, the extension can spawn a goroutine that continuously monitors the ring buffer for new entries. Perhaps it can remember the last index it has seen and periodically (or event-driven) check for new writes. However, polling could introduce latency or CPU overhead. Ideally, the processor (writer) can signal that new data was added. We could implement a simple **pub-sub** internally: when the processor writes to the ring buffer, it also broadcasts an event (could be a channel) to any listeners. The extension, upon a new subscription, registers as a listener (with its filter criteria). 

For example, we maintain for each data type a list of active subscribers (with their filter). After adding a new telemetry item to the buffer, the processor invokes a callback or sends on a channel that carries the item (or its index). The extension side can receive that and check which subscriptions match the item, then immediately stream it out. This would achieve real-time pushing with minimal delay. To avoid complicated thread management, each subscription can run on its own goroutine that waits on a channel of new items, filtering those relevant. We must ensure proper synchronization such that writing to the buffer and sending on channels is thread-safe and non-blocking. Possibly use buffered channels or a non-blocking select to drop notifications if subscriber is slow (assuming the data is anyway in the buffer, the subscriber can catch up by also scanning differences).

We should also consider backpressure: if a subscriber cannot keep up (slow network or client), the gRPC stream could get backed up. We might need to drop oldest data in that stream (since the buffer will anyway overwrite old data). This is an edge case; a reasonable approach is to document that the streaming is best effort and if the buffer overwrites data before the client could receive it, that data is lost (similar to any real-time feed).

**Authentication/Authorization:** If the Collector is running in a production environment, exposing a query API might require auth (especially as it could expose sensitive telemetry). The OTEL Collector supports authenticators (extensions that can be plugged into receivers or exporters) ([Building an authenticator extension - OpenTelemetry](https://opentelemetry.io/docs/collector/building/authenticator-extension/#:~:text=The%20OpenTelemetry%20Collector%20allows%20receivers,to%20both%20authenticate%20incoming)). We may incorporate an authentication check in our gRPC server. If needed, we can reuse OTEL's gRPC server settings ([opentelemetry-collector/config/configgrpc/README.md at main](https://github.com/open-telemetry/opentelemetry-collector/blob/main/config/configgrpc/README.md#:~:text=gRPC%20exposes%20a%20variety%20of,within%20individual%20receivers%20or%20exporters)) to enforce TLS or mTLS on this endpoint. These details can be configured similarly to a receiver (since we’ll likely open our gRPC on a specific port with possible TLS settings). For now, assume it’s an internal tool or secured by network and tackle auth if needed via extension.

**API Data Example:** A sample usage: A user wants to get recent spans for a service “checkout” in the last 5 minutes. They call `QueryTraces` with `resource_attr["service.name"]="checkout"` and `start_time = now-5m`. The service scans the trace ring buffer, finds all spans matching, and returns them in a `TraceQueryResponse` containing ResourceSpans. The user could also call `SubscribeTraces` with the same filter to continuously receive new spans from “checkout” service in real-time as they are received by the collector. This can greatly help in live debugging scenarios (much like how **Fluent Bit’s “TAP” feature allows live tapping of logs flowing through a pipeline for troubleshooting ([v2.0.1](https://fluentbit.io/announcements/v2.0.1/#:~:text=One%20of%20the%20common%20questions,troubleshooting%20without%20stopping%20the%20agent))). Our service would provide a unified way to do this for traces, metrics, and logs.

## Performance Considerations and Configuration Options  
Designing for performance and configurability is crucial since telemetry pipelines can be high throughput. Here we consider potential bottlenecks and how to mitigate them:

- **Memory Overhead:** By definition, the ring buffer is bounded in size. The configuration should make clear how memory is affected. For example, storing 10,000 spans could consume roughly the size of 10,000 span objects plus overhead. If each span is, say, 1KB, that’s ~10 MB – which is fine. Metrics might be bulkier (one metrics batch could be dozens of kilobytes if it contains many data points). We should allow sizing by **number of items** and possibly by approximate memory. If memory usage is a concern, we could also allow compressing or truncating stored data (for example, maybe we don’t need to store the full trace event attributes for all spans if just querying by IDs; but likely it’s fine to store full data for fidelity). The user must be aware that too large a buffer can increase Collector’s memory footprint. On the other hand, too small a buffer might drop data before it can be queried. It’s a trade-off to configure per environment.

- **Lock Contention:** If the collector is receiving a very high volume of telemetry (say thousands of spans per second) and simultaneously multiple clients are querying, the ring buffer lock could become a contention point. To reduce this, we use separate buffers per data type (so trace writes don’t block log writes, etc.). Within a buffer, writes and reads may conflict. We can minimize the critical section – e.g., writing a span to the buffer can be just a few pointer assignments and index increments, which will be very fast (microseconds). Reads (queries) might iterate over up to N items; if N is large, holding a read lock (in case of RWLock) might block a write for longer. A possible enhancement is to make a snapshot of the buffer for reading: e.g., copy the current buffer content (or the portion in range) under lock, then release lock and filter the copy. This way, the lock is held only briefly while copying references. Given modern hardware, copying, say, 10k pointers is trivial, so this could be a good strategy for heavy usage scenarios.

- **Lock-Free Options:** As mentioned, using an atomic ring buffer (like Disruptor) could eliminate locks for producers. That design can allow multiple producers and one or multiple consumers without mutexes by using sequence numbers ([Optimizing OpenTelemetry's Span Processor for High Throughput and Low CPU Costs](https://careersatdoordash.com/blog/optimizing-opentelemetrys-span-processor/#:~:text=,available%20for%20consumers%20to%20read)). If we foresee truly high throughput (hundreds of thousands of events per second) and want minimal overhead, this is an option. However, implementing a correct lock-free ring buffer with multi-consumer support is complex. The Go `go-disruptor` library could be leveraged if needed, or even a wait-free single-writer multi-reader ring buffer pattern (since the processor is effectively a single pipeline stage per data type, we might have at most a few producers). At initial stage, we prioritize clarity, then profile. The system should be designed such that the buffering can be turned off if it becomes a bottleneck (so maybe the processor can be disabled dynamically or configured off, to not impact the main pipeline if not needed).

- **Impact on Collector Throughput:** We should test how much overhead the buffering adds. The OTEL Collector is often deployed to handle high volumes and we must ensure that enabling this feature doesn’t drastically reduce throughput or increase latency of exports. The batch processor in OTEL typically uses an internal queue and is quite efficient, so adding one more copy of data into a ring buffer likely has marginal cost. If our processor does heavy work (like complex filtering or large copies) it could slow things. We will keep processor logic minimal: essentially just append to buffer and forward the data to next consumer (so that normal exporting continues). We can mark our processor as non-mutating (via `GetCapabilities` returning `MutatesData: false`) so the Collector knows it’s just a pass-through with a side effect ([Extending the OpenTelemetry Collector with your own components | by Juraci Paixão Kröhling | OpenTelemetry | Medium](https://medium.com/opentelemetry/extending-the-opentelemetry-collector-with-your-own-components-64c10cf675db#:~:text=explaining%20the%20,to%20possibly%20apply%20some%20optimizations)). This helps ensure upstream optimizations remain valid.

- **Real-time Streaming Performance:** Pushing data to clients in immediate mode means each incoming telemetry item might trigger network sends. If there are many subscribers or the subscriber is slow, this could back up. We should consider limiting how many streams can be open or what volume we push. Perhaps provide a config for **max concurrent subscribers** to avoid resource exhaustion. If one client subscribes without filters (meaning “send me everything in real-time”), that could effectively double the work: every event is now not only processed in pipeline but also cloned to a gRPC stream. This could be heavy. In such a scenario, a user probably only does that in testing, but if they attempt it in production, it could be problematic. We might suggest in documentation to use selective filters when subscribing. Or implement simple flow control: if a client subscribes to everything, maybe limit the rate or buffer on the server side (to not OOM the server if the client can’t read as fast). 

- **Configuration Options:** In addition to buffer sizes, we should allow enabling/disabling the immediate streaming feature. For example, if not needed, the processor might not bother notifying any subscriber logic. If needed, the extension and processor coordinate via channels as described. We can also have a config to set the query gRPC **endpoint address** (host:port). By default maybe it listens on something like `0.0.0.0:4319` (just as 4317/4318 are OTLP; 4319 could be our query, or any port). Also possibly support TLS settings for that gRPC endpoint, which we can do by leveraging OTEL’s gRPC server utils ([opentelemetry-collector/config/configgrpc/README.md at main](https://github.com/open-telemetry/opentelemetry-collector/blob/main/config/configgrpc/README.md#:~:text=gRPC%20exposes%20a%20variety%20of,within%20individual%20receivers%20or%20exporters)). Optionally, a simple in-memory **cache** TTL could be configurable (like do we evict after X seconds regardless of buffer size or only by buffer overflow – mostly covered by ring semantics, but time-based flush could be considered to avoid stale data lingering if nothing new coming in).

- **Multi-tenancy and Isolation:** If the collector is scraping multiple distinct sources or acting as a global aggregator, the query service will be exposing data from all sources. That may be fine or may require the query to specify which pipeline or source to query from. Usually resource attributes cover the source (like service name, cluster, etc.), so filtering by those suffices. In advanced use, one could imagine each pipeline having its own buffer. An interesting alternative design: implement this as a **connector** or **forked pipeline** – e.g. use OTEL’s new connector interface to branch data to a local storage. Connectors (in OTEL) can route data between pipelines ([Configuration | OpenTelemetry](https://opentelemetry.io/docs/collector/configuration/#:~:text=Configuration%20structure)). We could have configured a pipeline that uses an exporter to local memory and then an extension reads from it. But that is overkill when a direct processor can do it. It’s worth noting the design is flexible enough to have one global buffer or separate ones per pipeline if needed for isolation (we can key entries by pipeline if needed in the data structure).

## Recommended Libraries and Patterns (Go and Alternatives)  
Since the OTEL Collector is written in Go and provides a Go SDK for custom components, using **Go** is the path of least resistance for implementation. We can take advantage of existing Collector packages and patterns:

- **OTEL Collector SDK:** Use the helper builders like `processorhelper.NewTracesProcessor` (and similarly for metrics, logs) to reduce boilerplate. These helpers let you focus on the `ConsumeTracesFunc` logic (where we would append to the buffer) and handle things like error handling and calling the next consumer ([Extending the OpenTelemetry Collector with your own components | by Juraci Paixão Kröhling | OpenTelemetry | Medium](https://medium.com/opentelemetry/extending-the-opentelemetry-collector-with-your-own-components-64c10cf675db#:~:text=Similar%20to%20what%20happens%20with,to%20satisfy%20the%20full%20interface)) ([Extending the OpenTelemetry Collector with your own components | by Juraci Paixão Kröhling | OpenTelemetry | Medium](https://medium.com/opentelemetry/extending-the-opentelemetry-collector-with-your-own-components-64c10cf675db#:~:text=across%20implementations%2C%20like%20,to%20satisfy%20the%20full%20interface)). Similarly for the extension, implement the `Start` method to spin up our gRPC server and `Shutdown` to gracefully stop it. The extension can use OTEL's logging and settings passed in `CreateSettings`. 

- **Protocol Buffers and gRPC in Go:** We will define our proto file for the query service and generate Go code (using `protoc`). The gRPC server in the extension can be created with `grpc.NewServer()` and we register our service implementation. One consideration: the OTLP receiver might already be using gRPC on a certain port. We should run our service on a **different port** (to avoid interfering with OTLP). For example, configure `extensions.telemetry_query.endpoint: 0.0.0.0:4320` (just a sample port). This is similar to how zPages extension uses its own HTTP port ([opentelemetry-collector/extension/zpagesextension/README.md at main · open-telemetry/opentelemetry-collector · GitHub](https://github.com/open-telemetry/opentelemetry-collector/blob/main/extension/zpagesextension/README.md#:~:text=The%20following%20settings%20are%20required%3A)). We can use `configgrpc` (OTEL Collector library) to parse common gRPC settings from our config if we allow TLS or compression settings ([opentelemetry-collector/config/configgrpc/README.md at main](https://github.com/open-telemetry/opentelemetry-collector/blob/main/config/configgrpc/README.md#:~:text=gRPC%20exposes%20a%20variety%20of,within%20individual%20receivers%20or%20exporters)).

- **Data Structures in Go:** For the ring buffer, if we choose not to implement from scratch, we might consider libraries: e.g. **`github.com/smallnest/ringbuffer`** which provides a thread-safe circular buffer implementing `io.Reader`/`Writer` interface (used typically for streaming data) ([GitHub - smallnest/ringbuffer: a thread-safe circular buffer (ring buffer) in Go, implemented io.ReaderWriter interface](https://github.com/smallnest/ringbuffer#:~:text=io)). This could be useful if we wanted a bytes-oriented buffer, but for our case, we need to store structured items, so a generic container is better. With Go 1.18+, we can also implement a generic ring buffer: a simple version using a slice of type `T` and atomic indices. There are community examples of a generic lock-free ring buffer using Go generics ([Implementing a Lock-Free Ring Buffer in Go | by Nathan B. Crocker](https://medium.com/@nathanbcrocker/implementing-a-lock-free-ring-buffer-in-go-ee36bba220ea#:~:text=Implementing%20a%20Lock,without%20any%20form%20of%20locking)), but again, correctness first. Another library, **go-disruptor** (from Smartystreets or five-vee as referenced above) could be used for a proven lock-free implementation if needed. It might be overkill initially, but we can keep it in mind if performance tests require it.

- **Design Patterns:** The producer-consumer pattern is inherent here. We will use it in two places: (1) pipeline to buffer (producer = collector pipeline, consumer = query service), and (2) buffer to streaming subscribers (producer = ring buffer new-entry notifier, consumer = gRPC stream). Go’s goroutines and channels are great for decoupling these and handling asynchronous events. For example, a channel can notify the extension about new data without blocking the main pipeline. We will carefully design these channels to avoid blocking. Possibly use a *non-blocking broadcast*: e.g., maintain an array of subscriber channels; when new item arrives, try sending to all, if a channel is full (slow consumer), we can drop the notification (the data is anyway in the buffer for them to retrieve later on a poll request). This ensures a slow subscriber doesn't stall the processor.

- **High-Performance Alternatives:** The user mentioned being open to other languages or systems if better. While one could imagine writing this component in a lower-level language for speed, it would complicate integration severely. The Collector’s component model is Go-based. A radical alternative could be running a separate high-performance service (in Rust or C++) that receives data from the collector (via an exporter) and provides query API. For instance, an **OpenTelemetry Collector Exporter** that sends data to a local Rust service (via shared memory or a local gRPC) which stores in a super optimized ring buffer structure (perhaps using lock-free and SIMD optimizations), and that Rust service provides queries. This might achieve performance wins but at a cost of complexity (two processes, data copying between them, etc.). In most cases, the Go implementation can be tuned to handle very high throughputs (the OTel Collector itself is used in production at high scale). So, we would typically **recommend staying with Go** for full compatibility. If profiling shows Go GC or locking is a bottleneck, one could consider using techniques like **memory pooling** (to reuse objects and reduce GC, perhaps using sync.Pool for spans) or the mentioned disruptor which is designed to minimize GC ([Optimizing OpenTelemetry's Span Processor for High Throughput and Low CPU Costs](https://careersatdoordash.com/blog/optimizing-opentelemetrys-span-processor/#:~:text=,available%20for%20consumers%20to%20read)). 

- **Testing and Debugging Tools:** We can use the Collector’s own testing harness to ensure our processor and extension work. Also, using the custom distribution approach, we can run an instance with our component and use a test client to send OTLP data and then query it. Tools like **ghz** (gRPC benchmarking) could test query throughput. Because we integrate at a low level, standard OTEL Collector tests (like correctness of data passed through) should be done: ensure that the processor does not modify data (unless intended) and does not leak memory.

## Related Work and Inspirations  
This idea of buffering and querying telemetry locally is somewhat atypical for OpenTelemetry (which usually pushes data out to external backends for storage and querying). However, there are several analogous projects and features to draw inspiration from:

- **Jaeger All-in-One (OTEL-based)**: As mentioned, Jaeger’s latest architecture (Jaeger v2) builds on the OTEL Collector. In Jaeger’s all-in-one mode with in-memory storage, spans are buffered in memory and a query UI is provided ([Architecture — Jaeger documentation
](https://www.jaegertracing.io/docs/next-release-v2/architecture/#:~:text=,metrics%20%26%20logs)) ([Architecture — Jaeger documentation
](https://www.jaegertracing.io/docs/next-release-v2/architecture/#:~:text=The%20all,is%20limited%20to%20a%20single)). Our design is a generalized version of that concept. Jaeger’s implementation includes a **Query extension** (to serve the Jaeger query API and UI) and an in-memory storage component ([Architecture — Jaeger documentation
](https://www.jaegertracing.io/docs/next-release-v2/architecture/#:~:text=,access%20to%20Jaeger%20storage%20implementations)). Studying Jaeger’s source (especially the `Jaeger Query Extension` ([Architecture — Jaeger documentation
](https://www.jaegertracing.io/docs/next-release-v2/architecture/#:~:text=storage%20backend%20configured%20in%20the,Jaeger%20Storage%20Extension)) and `Memory Storage` components) can provide guidance on how they manage the in-memory data and expose APIs. One difference is that Jaeger’s query is primarily for traces, whereas our plan covers metrics and logs as well.

- **OpenTelemetry zPages**: The Collector’s zPages extension provides in-process debugging webpages ([opentelemetry-collector/extension/zpagesextension/README.md at main · open-telemetry/opentelemetry-collector · GitHub](https://github.com/open-telemetry/opentelemetry-collector/blob/main/extension/zpagesextension/README.md#:~:text=Enables%20an%20extension%20that%20serves,receivers%20provide%20some%20zPage%20instrumentation)). Notably, **TraceZ** page gives a snapshot of recent spans and their latencies ([opentelemetry-collector/extension/zpagesextension/README.md at main · open-telemetry/opentelemetry-collector · GitHub](https://github.com/open-telemetry/opentelemetry-collector/blob/main/extension/zpagesextension/README.md#:~:text=TraceZ)). Under the hood, zPages in OpenTelemetry (inspired by OpenCensus zPages) keeps track of recent spans in memory for debugging. While zPages is not as flexible (no custom queries, just a UI webpage with fixed categories), it confirms the value of in-memory telemetry for quick access without a backend. Our ring buffer could be seen as a programmatic version of zPages, and we might even reuse some of the instrumentation that zPages extension has (if any) to collect data. However, zPages likely works by each component reporting to it, rather than capturing all data. In contrast, our processor ensures *all* incoming telemetry can be stored.

- **Fluent Bit “TAP” and Memory Buffer**: Fluent Bit, a log forwarding agent, introduced a **TAP feature** that allows users to tap into the data stream in real-time via an HTTP request for troubleshooting ([v2.0.1](https://fluentbit.io/announcements/v2.0.1/#:~:text=One%20of%20the%20common%20questions,troubleshooting%20without%20stopping%20the%20agent)). This is conceptually similar to our immediate mode for logs. They also have an in-memory ring buffer option for buffering logs (to avoid disk I/O), configured by a mem_buf_limit ([v2.0.1](https://fluentbit.io/announcements/v2.0.1/#:~:text=The%20memory,is%20enabled%2C%20the%20chunks%20management)). This shows that ring buffers are used in logging pipelines for non-blocking, bounded buffering. We can take inspiration from how Fluent Bit allows toggling this at runtime and how it ensures minimal performance hit. Our solution being baked into the Collector would be configured upfront, but could similarly be turned on/off as needed for troubleshooting.

- **Monitoring Tools & Live Tail**: Many logging and monitoring systems offer a “live tail” feature (e.g., `kubectl logs -f` for Kubernetes, or Splunk’s live tail, etc.), which underneath use either polling or streaming to fetch recent data from a buffer. Similarly, some APM tools allow fetching recent traces on demand. While not open-source references, they justify the usefulness. Our implementation essentially provides a foundation to build such capabilities in a vendor-neutral way.

- **CNCF Projects**: Projects like **Loki** (for logs) or **Grafana Tempo** (for traces) focus on storing telemetry in backends, but Tempo has a feature called *search* when used with its **Cache**. Tempo can keep recent traces in an in-memory cache (like a block in memory) to allow quick retrieval before they are persisted. This is akin to our ring buffer (though Tempo’s cache is eventually written out). This pattern of recent-data cache could be cited as similar motivation.

- **Prior Art in OpenCensus**: OpenCensus (an ancestor to OpenTelemetry) had a feature to register in-memory exporters that could be queried or inspected. While not exactly the same, it showed the idea of diverting telemetry to a local store for inspection. 

In summary, while no off-the-shelf component provides exactly what we’re building, the components above validate each piece of the design: ring buffers for telemetry (OTEL, FluentBit), in-process query services (Jaeger, zPages), and streaming outputs (FluentBit TAP, gRPC streaming telemetry in network devices). We will combine these ideas following best practices of the OTEL Collector ecosystem. 

## Implementation Plan Summary  
To conclude, implementing the ring-buffer query service in the OTEL Collector will involve these steps:

1. **Define Protobuf and Service** for the Telemetry Query API (covering query requests for traces, metrics, logs and streaming capabilities). Generate Go code for the service interface and messages.

2. **Implement the Processor** (`telemetrybufferprocessor`): handle `ConsumeTraces`, `ConsumeMetrics`, `ConsumeLogs`. In each, loop through items and append to the respective ring buffer (with proper synchronization). Then forward the data to next consumer (so normal export continues). Support configuration for buffer sizes. (If needed, implement helper routines for indexing by trace ID, etc.)

3. **Implement the Extension** (`telemetryqueryextension`): on Start, create a gRPC server listening on the configured endpoint. Register the query service implementation. The implementation should have access to the ring buffers (perhaps via package-level vars or by obtaining the processor instance. A simple method is to have the processor register itself (or its buffers) in a global registry that the extension can import, or to use dependency injection if the Collector’s service context allows passing references – currently not automatic, so likely a global or singleton). Ensure the extension starts after the processor (the Collector’s service extensions ordering can be specified ([opentelemetry-collector/extension/README.md at main · open-telemetry/opentelemetry-collector · GitHub](https://github.com/open-telemetry/opentelemetry-collector/blob/main/extension/README.md#:~:text=The%20order%20extensions%20are%20specified,in%20the%20configuration%20file%2C%20example)) so we can list it after pipelines start). On Shutdown, stop the gRPC server.

4. **Query Handling**: In the service methods, implement filtering logic to retrieve data from buffers. For unary (non-streaming) queries, do a one-time scan and return results. For streaming, spawn goroutines to push new data: possibly use a channel subscription model as described. Take care to handle client cancellation (gRPC context cancellation) to break out of loops.

5. **Testing**: Write unit tests for ring buffer wrap-around, for filtering logic, etc. Possibly simulate multiple writers and readers to ensure thread safety. Integration test by running a minimal collector with our components: send in a few spans via OTLP, then query via our gRPC and verify the data matches.

6. **Documentation and Usage**: Document how to configure (e.g. enabling the processor in pipelines and adding the extension under `service.extensions`). Provide guidance on suitable buffer sizes and note the experimental nature if it’s first iteration.

By following this plan, we add a powerful capability to the OpenTelemetry Collector: the ability to query recent telemetry in-memory, enabling rapid troubleshooting and ad-hoc analysis without requiring a full backend. This solution balances the needs for performance (using efficient ring buffers ([Optimizing OpenTelemetry's Span Processor for High Throughput and Low CPU Costs](https://careersatdoordash.com/blog/optimizing-opentelemetrys-span-processor/#:~:text=,available%20for%20consumers%20to%20read))) with the flexibility of OTEL’s component model and gRPC streaming. It can serve as a foundational block for building more user-friendly features (for example, one could build a small web UI or CLI on top of this query API to allow developers to inspect their system’s telemetry in real time, much like a built-in observability console).
